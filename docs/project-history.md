# Orrery: project history

A record of the whole Orrery project, from the first idea to the Vercel shutdown. It covers what was built, how it was built, the decisions made along the way and where everything lives now.

- **Status:** Finished and frozen. The public Vercel demo was deleted on 2026-09-15.
- **Repository:** https://github.com/zetabytelab/orrery (public, Apache-2.0).
- **Video:** https://youtu.be/z7agJOrHa9I (2:48)
- **Built for:** Build with DataHub: The Agent Hackathon (Devpost). Category: Open / Wildcard, with overlap into Production ML Agents. Deadline: 2026-08-10, 17:00 ET.
- **Active development:** 2026-08-05 to 2026-08-10, 25 commits. About 2,200 lines of TypeScript, Python and JS.

---

## 1. The idea

Data catalogs and data profilers describe the same data but rarely meet:

- A **catalog** like DataHub records what *should* be true: schemas, lineage and ownership.
- A **profiler** measures what *is* true: nulls, types and value distributions.

Orrery puts both on one canvas and treats the gap between them as the product. Take a column that DataHub declares as `timestamp` where 9% of the actual values are epoch-millis integers. That is a broken contract. Because the lineage is real, Orrery can show which ML model and which executive dashboard the problem reaches, which teams to notify, what the problem costs and what could replace the broken data. It then writes all of that back into DataHub.

The name comes from the orrery, a clockwork model of the solar system. It is small enough to sit on a desk and accurate enough to predict an eclipse. This one models a data estate accurately enough to predict which dashboards go dark.

**Tagline:** *See the blast radius before it hits.*

## 2. How the idea changed

1. **The first entry was the Wildfire Lifeboat (2026-08-05).** It was built as a feature of Mundaneum, the dataset-discovery CLI. It added EFFIS and FIRMS wildfire data sources, a wildfire exposure report and composite rescue bundles.
2. **The entry then switched to Orrery (evening of 2026-08-05).** The wildfire work showed the "lifeboat" concept (finding replacement data for a broken dependency) was strong. Orrery was a better fit for the DataHub hackathon, and the lifeboat idea carried over as its rescue feature.
3. **Orrery got its own public repo**, separate from Mundaneum.

## 3. What Orrery does

| Capability | What the user sees |
|---|---|
| **Infinite canvas** | The DataHub lineage graph drawn with React Flow and a dagre layout. Zoomed out, it is a constellation colored by data health. Zoomed in, each dataset is a full profiling card. |
| **In-browser profiling** | DuckDB-Wasm profiles every dataset live: types, missing %, distinct counts, min/max, histograms, top-k values and text patterns. No warehouse or profiling jobs are needed. |
| **Contract checks** | Each column's declared DataHub type is compared with its observed type. Mismatches become type-drift or contract-violation issues. |
| **Incident propagation** | Clicking a broken column animates its downstream reach along real lineage. ML models and dashboards get an "upstream quality incident" badge. |
| **Impact panel** | Shows the blast radius, the owners of affected assets and the teams to notify. |
| **FinOps exposure** | Prices each incident from the data itself: revenue per day steered by affected dashboards, at-risk customers under the affected model, and a repair estimate with its assumptions shown. Framed by the 1-10-100 data-quality cost rule. |
| **Rescue lifeboat** | For serious incidents, ranks replacement datasets from Mundaneum's cross-catalog directory of 40k+ datasets (Databricks and Snowflake marketplaces, Kaggle, Hugging Face, Datarade, data.gov and more), with license, pricing and quality details. |
| **Write-back to DataHub** | Sends findings through the official DataHub MCP server: a profile note (`update_description`), severity tags down to the exact column (`add_tags` with `column_paths`) and a rescue proposal filed as a DataHub Document (`save_document`). |

### The demo estate

A synthetic, deterministic commerce stack of about 15k rows, generated by `data/generate-estate.mjs`:

```
raw_orders ─→ stg_orders ─────→ fct_revenue_daily ───→ exec_revenue_dashboard (Looker)
raw_customers → stg_customers ─→ dim_customer_health ─→ churn_model (MLflow)
raw_events ──→ stg_events ──────┘
```

It has two seeded incidents. Both were chosen because ordinary schema checks cannot catch them:

1. **`stg_customers.email`: 13.3% of emails were silently blanked** by a consent-scrubber bug. An empty string is still a valid string, so every pipeline stays green, while churn outreach quietly loses its most at-risk customers.
2. **`stg_events.event_ts`: 9.3% of values are epoch-millis integers** because an upstream producer drifted. DataHub still says `timestamp`, but the observed type is `VARCHAR`.

Both incidents reach **100% of the decision layer**: the churn model and the executive dashboard.

**Headline figures, all measured from the data:** about **€30,034/day** of revenue steered by the affected dashboard, **143** high-churn-risk customers exposed and about **€935** (8.5 hours) to fix.

## 4. Architecture

```
┌────────────────────────── browser ──────────────────────────┐
│  React Flow canvas (semantic zoom, dagre layout)            │
│  DuckDB-Wasm profiling engine + contract checks             │
└──────────────┬──────────────────────────────────────────────┘
               │ /api/context   /api/writeback   /api/rescue
┌──────────────┴──────────────────────────────────────────────┐
│  Next.js API routes: MCP client (stdio)                     │
│    └─ uvx mcp-server-datahub  ⇄  DataHub GMS                │
│  fixture fallback: fixtures/estate.json, fixtures/rescue.json│
└─────────────────────────────────────────────────────────────┘
```

**Stack:** Next.js 16.3, React 19, React Flow (`@xyflow/react`), dagre, DuckDB-Wasm, MCP TypeScript SDK, Tailwind 4 and lucide icons. Demo ingestion into DataHub uses the Python `acryl-datahub` SDK.

**Two modes:**

- **Zero-config fixture mode.** This is the default. It uses the bundled estate and rescue snapshot, and write-back shows the exact MCP calls as a dry run.
- **Live mode.** It turns on when `DATAHUB_GMS_URL` is set (optionally with `DATAHUB_GMS_TOKEN` and `ORRERY_DATAHUB_QUERY`, which defaults to `orrery`). The estate is then read with MCP `search`, `list_schema_fields` and `get_lineage`, and write-back changes the real catalog.

### Feedback given to the DataHub team

These six friction points came up while building and went into the survey:

1. `mcp-server-datahub` only supports stdio, and a Streamable HTTP transport would make it usable from web backends.
2. The JSON shapes of MCP tool results are undocumented, so building a typed client needed defensive parsing.
3. Remapping quickstart ports (`DATAHUB_MAPPED_*_PORT`) is hard to discover, and failures show a generic error.
4. The quickstart pulls about 18 GB of images with no progress display and no slim profile.
5. `add_tags` assumes the tags already exist, and a `create_if_missing` option would help.
6. The quickstart ignores Docker CLI contexts. With both Docker Desktop and OrbStack installed, it deployed to the other engine.

## 7. Lessons and gotchas

- **The DataHub quickstart follows whatever owns `/var/run/docker.sock`** which may not be the engine `docker context` reports.
- **`docker compose down -v` does not remove quickstart volumes.** Use `datahub docker nuke` to get a clean catalog.
- **MCP mutation tools require `TOOLS_IS_MUTATION_ENABLED=true`.** Orrery sets it when it spawns the server.
- **Vercel serverless functions do not include runtime-read files automatically.** List them in `outputFileTracingIncludes`.
- **Every finding is tied to evidence:** a named column, a measured percentage and a declared-vs-observed check, with no unexplained AI scores. This choice shaped both the product and the pitch.
